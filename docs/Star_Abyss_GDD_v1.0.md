# 星渊遗迹（Star Abyss）游戏策划文档 GDD v1.0

> 文档状态：开发基线 / 2026-10-22  
> 目标读者：Codex、Godot 开发代理、BlenderMCP 美术代理、人工验收者  
> 规则：本文件是玩法与范围的单一事实来源。未明确规定的实现细节可以合理选择，但不得擅自扩大 MVP 范围。下列数值均为**首轮测试值**，不是最终平衡结论。

## 1. 项目概述

| 项目 | 约定 |
|---|---|
| 游戏名称 | 星渊遗迹 / Star Abyss（暂定） |
| 类型 | 单人第三人称 3D 动作 Roguelite |
| 画风 | 二次元卡通渲染（Cel / Toon Shading） |
| 引擎 | Godot 4.x 稳定版，GDScript |
| 美术 | Blender，优先 glTF 2.0 / GLB 交付 |
| 平台 | Windows PC，键盘鼠标优先 |
| 单局目标 | 完整版 10–15 分钟；MVP 约 5–8 分钟 |
| 开发方式 | Codex 主导代码和自动化，BlenderMCP 辅助资产，人工确认手感和美术 |
| 性能目标 | 1080p 中档独立显卡 60 FPS（目标，需实测） |

### 1.1 一句话卖点
在充满古代魔法装置的遗迹中，以灵活的闪避和三段剑击击败敌人，每过一间房选择随机祝福，组合出不同的战斗风格，最终挑战晶核守卫。

### 1.2 设计支柱
1. **先有手感**：移动、攻击命中、闪避和敌人预警必须清晰。
2. **短局高复玩**：少量房间、随机强化、快速重开。
3. **可读性优先**：卡通画风服务于敌我辨识、攻击预警和伤害反馈。
4. **资产可复用**：模块化房间、统一骨骼与动画、数据驱动技能。
5. **小范围可交付**：先做完整闭环，再增加内容数量。

### 1.3 非目标
MVP 不开发联网、联机、开放世界、抽卡、复杂装备、剧情对话树、任务系统、程序化地形、永久成长、云存档、移动端和手柄支持。

## 2. 世界观与叙事

昔日文明依靠“星渊晶核”驱动城市。晶核失控后，遗迹被能量侵蚀，守卫机械逐渐失去控制。玩家扮演“遗迹探索者”，进入封闭试炼区，收集祝福并击败核心守卫，暂时稳定晶核。

MVP 仅通过标题、关卡环境、Boss 名称和结算文字传达设定，不制作过场动画或复杂剧情。避免让叙事阻碍重复游玩。

## 3. 核心游戏循环

**主菜单 → 开始本局 → 房间 1 战斗 → 祝福三选一 → 房间 2 战斗 → 祝福三选一 → 房间 3 Boss → 胜利/失败结算 → 重新开始/主菜单。**

### 3.1 房间结构
- 房间 1：教学式普通战斗，2 只近战敌人，击败后获得祝福。
- 房间 2：进阶普通战斗，3 只近战敌人，击败后获得祝福。
- 房间 3：Boss 战，1 名晶核守卫；击败后胜利。
- MVP 使用固定房间顺序和固定几何结构；**祝福候选随机**，而非地图随机。
- 进入战斗房间后关闭出口；清除全部敌人后开放出口并触发祝福选择（Boss 房除外）。
- 每局从满血开始；跨房间保留当前生命值和祝福；重新开始清空本局祝福。

### 3.2 胜负与重开
- 玩家 HP ≤ 0：进入失败结算，暂停战斗输入，展示已通过房间数与用时。
- Boss HP ≤ 0：进入胜利结算，展示用时、击杀数、祝福列表。
- 结算按钮：重新开始、返回主菜单；重开后所有运行态数据复位。
- 失败不保留进度，MVP 不实现局外成长。

### 4.2 摄像机
- 第三人称斜后方，默认跟随距离 4.5 m，目标高度约 1.4 m。
- 默认俯仰角 -12°，允许范围 -55° 至 +35°（实际坐标符号按实现统一）。
- 鼠标灵敏度可配置；使用 SpringArm3D 避免穿墙。
- 角色移动相对摄像机水平前向，不因镜头俯仰产生垂直移动。
- 攻击时允许小幅调整朝向；镜头不能突然强制转向敌人。

### 4.3 状态机与优先级
基础状态：Idle、Move、Jump、Fall、Attack、Dodge、Skill、Hurt、Dead。状态切换由独立 FSM 控制。
- Dead 优先级最高，不允许再接收战斗输入。
- Dodge 可从 Idle/Move 发起；不能在硬直或死亡状态发起。
- Attack 期间仅在配置的取消窗口允许闪避；不允许无限取消动作。
- Skill 期间默认不可被普通攻击打断，可被死亡终止。
- 输入缓冲窗口：0.18 s，用于连击衔接。
- 受击硬直与无敌区间由独立组件维护，避免 FSM 与伤害系统相互写死。

## 5. 战斗系统

### 5.1 三段普通攻击
| 段数 | 基础伤害 | 动作总长 | 命中窗口 | 说明 |
|---|---:|---:|---|---|
| 1 | 12 | 0.48 s | 0.16–0.28 s | 快速横斩 |
| 2 | 16 | 0.56 s | 0.20–0.34 s | 反向斩击 |
| 3 | 24 | 0.72 s | 0.25–0.44 s | 重击，明显收招 |

- 每段攻击最多对同一目标命中一次；一次挥击可命中多个目标。
- 连击窗口在当前攻击中后段开放；缓冲的下一击只在允许窗口衔接。
- 连击中断 0.9 s 后重置为第一段。
- 命中产生受击闪白、短促停顿（Hit Stop，初值 0.04 s）、音效与伤害数字；特效不得影响实际伤害结算次数。
- MVP 不做复杂空中连击、格挡、弹反或武器切换。

### 5.2 主动技能：星刃斩
- E 触发一次前方扇形剑气，范围 5 m，扇形夹角 70°。
- 基础伤害 35，冷却 8 s；技能动作总长 0.7 s。
- 同一目标每次施放最多受击一次。
- 技能无额外资源消耗；释放期间不能连续施放。

### 5.3 伤害与生命
- MVP 采用简单模型：`最终伤害 = max(1, round(基础伤害 × 攻击倍率 × 目标承伤倍率))`。
- 初版攻击倍率、承伤倍率默认为 1.0；祝福可以修改倍率。
- 不实现护甲、暴击、元素抗性、等级差等复杂公式。
- 伤害来源必须带唯一攻击实例 ID，Hitbox 按攻击实例记录已命中目标，避免重复扣血。
- 无敌时伤害为 0，且不触发硬直；死亡仅结算一次。
- 玩家受伤后有 0.5 s 受击保护（可调）；Boss 大招不能无预警瞬间击杀满血玩家。

### 5.4 战斗可读性
- 玩家攻击轨迹使用浅蓝色，敌方攻击预警使用红橙色。
- Boss 预警应先于实际伤害判定出现，且预警区与实际判定尽量一致。
- 伤害数字与 UI 不应遮挡敌人动作；闪屏与震动强度可配置。

## 6. 敌人设计

### 6.1 普通敌人：遗迹哨兵
| 属性 | 初始值 |
|---|---:|
| HP | 45 |
| 移动速度 | 3.2 m/s |
| 追击感知半径 | 10 m |
| 攻击触发距离 | 1.8 m |
| 普通攻击伤害 | 10 |
| 攻击预警 | 0.55 s |
| 攻击生效窗口 | 0.18 s |
| 攻击后摇 | 0.55 s |
| 攻击冷却 | 1.3 s |

行为：Idle → Chase → Telegraph → Attack → Recover → Chase；死亡进入 Dead。
- 有效导航时追击玩家；超出范围或路径不可达时回到可用位置，避免卡墙持续攻击。
- 攻击前必须出现明显预警；一次攻击仅能对玩家造成一次伤害。
- 房间战斗可容许多敌人，但需限制同时近身攻击的数量，避免无法躲避的重叠攻击。

### 6.2 Boss：晶核守卫
| 属性 | 初始值 |
|---|---:|
| HP | 350 |
| 移动速度 | 2.6 m/s |
| 招式 A：重锤横扫 | 20 伤害，前摇 0.8 s，近身扇形 |
| 招式 B：晶能冲击 | 25 伤害，前摇 1.2 s，地面圆形范围 |
| 招式间隔 | 1.6–2.4 s |

- Boss 至少具备追击、招式选择、预警、攻击、恢复、死亡状态。
- 70% HP 以下可提高攻击频率约 15%，但 MVP 不强制增加新招式。
- 招式 B 在地面显示明显危险区域；危险区必须先预警后造成伤害。
- Boss 生命条置于屏幕上方，死亡后立即停止所有未完成攻击判定。

## 7. Roguelite 祝福系统

### 7.1 MVP 规则
- 通过普通战斗房间后，从 3 个不同祝福中选择 1 个。
- MVP 祝福池只有 3 个，因此每次展示这 3 个并随机排列；避免出现候选重复。
- 同一种祝福每局最多获得一次；第二次选择时，已获得祝福不再出现。如果剩余祝福少于 3 个，则显示剩余全部候选。
- 每次新开局重置祝福集合；通过可设定随机种子支持复现。
- 不实现稀有度、等级堆叠、装备栏、货币或商店。

### 7.2 MVP 三个祝福
| 祝福 ID | 名称 | 效果 |
|---|---|---|
| `blessing_flame` | 烈焰之刃 | 普通攻击最终伤害 × 1.20 |
| `blessing_wind` | 疾风步伐 | 闪避冷却由 1.2 s 降至 0.9 s |
| `blessing_vitality` | 生命共鸣 | 获得时立即恢复 20 HP（不超过上限），之后每次击杀普通敌人恢复 5 HP |

祝福通过 Resource 定义元数据和效果参数，由 BlessingManager 统一应用/撤销。禁止将祝福效果直接散落到 UI 按钮或单一巨型 Player 脚本。

### 7.3 后续扩展（非 MVP）
烈焰点燃、雷电连锁、暴击、护盾、冰冻、技能变体、祝福组合联动、局外升级、稀有度和更多角色。

## 8. UI / UX

必须具备：主菜单、HUD、暂停菜单、祝福选择、Boss 血条、胜利/失败结算。

- HUD 左上：HP 条与当前 HP；右下：E 技能冷却、Shift 闪避冷却；屏幕中央仅保留必要的战斗反馈。
- 祝福界面：暂停战斗，显示 1–3 张可点击卡片，含名称、简短效果和图标；选择后恢复游戏。
- 暂停菜单：继续、重新开始、返回主菜单；弹窗期间屏蔽游戏战斗输入。
- 结算：胜负、用时、击杀数、获得祝福，两个明确操作按钮。
- 文字语言：MVP 简体中文；数据结构预留多语言 key，不要求完成翻译系统。
- 分辨率：以 1920×1080 布局为基准，支持窗口缩放和常见 16:9 分辨率。

## 9. 美术与动画规范

### 9.1 视觉方向
- 风格：清晰的二次元 3D 卡通渲染，色块分明，适度描边，非写实 PBR 质感。
- 场景：灰蓝色古代遗迹、青色晶体发光、暖色敌方危险预警。
- 人物：轮廓清晰、材质分区明确、发型与服装细节克制，保证动作可读性。
- 特效：攻击方向明确，避免全屏高亮粒子遮挡攻击预警。

### 9.2 Blender 资产交付
- 保留 `.blend` 源文件，向 Godot 输出 `.glb`。
- 统一以米为单位；应用模型缩放；统一角色正前方与骨骼朝向，导出前执行检查。
- 玩家目标身高约 1.75 m；武器作为独立资产绑定至武器挂点。
- 模型命名：`CHR_Player_01`、`ENM_Sentinel_01`、`BOS_CoreGuardian_01`、`ENV_Ruins_Pillar_A`。
- 动画命名：`Idle`、`Run`、`Jump`、`Fall`、`Dodge`、`Attack_01`、`Attack_02`、`Attack_03`、`Skill_01`、`Hurt`、`Death`。
- MVP 首先用占位几何体或简化骨骼模型验证玩法；正式角色建模不得阻塞 P0–P5 开发。
- Blender 材质不要求在 Godot 中完全还原；Toon 材质在 Godot 中统一维护。

### 9.3 资产验收
- 模型导入后无明显变形、反向法线、错误缩放或武器错位。
- 动画根运动策略统一：MVP 采用代码驱动位移，动画仅表现动作，避免双重位移。
- 近战命中窗口与动画关键帧对应，不能仅凭固定计时猜测视觉命中。

## 10. 技术架构

### 10.1 核心原则
- Godot 4.x + GDScript；场景组件化，配置使用自定义 Resource。
- 玩家、敌人共享 HealthComponent、Hitbox、Hurtbox、DamageInfo 等基础概念。
- 玩家 FSM 和敌人 FSM 独立；不要把 AI 逻辑写进玩家控制器。
- 用 Signal 传播 HP 变化、死亡、房间完成、祝福选择等事件。
- Autoload 仅用于必要的 GameSession/SceneFlow，不创建无边界的万能管理器。
- 随机数通过本局 RNG 管理，记录种子，便于复现。

### 10.3 主要系统职责
| 系统 | 职责 |
|---|---|
| PlayerController | 输入、移动、朝向，不直接计算伤害 |
| CameraController | 跟随、旋转、碰撞避障 |
| PlayerStateMachine | 动作状态和合法切换 |
| CombatResolver | 统一伤害规则与命中实例去重 |
| HealthComponent | HP、无敌、死亡信号 |
| EnemyBrain | 感知、追击、招式决策 |
| RoomController | 敌人生成、清场、门状态 |
| RunManager | 当前房间、用时、击杀、祝福、胜负 |
| BlessingManager | 候选生成、效果应用、清理 |
| UIController | HUD 和界面状态，不持有核心玩法真值 |

### 10.4 可测试性
- 关键数值集中于 Resource，允许不改代码调参。
- 提供调试面板或日志显示 FSM 状态、HP、技能 CD、房间状态和随机种子。
- 自动检查项目资源引用、脚本解析和场景加载；人工验证手感、视觉、音效和帧率。
- 所有未实际运行的检查必须标注“未验证”，不得宣称通过。

## 12. MVP 验收测试

### 12.1 基础功能
- [ ] Windows 上可启动项目、进入主菜单并开始游戏。
- [ ] WASD、鼠标、Space、Shift、左键、E、Esc 功能正确。
- [ ] 摄像机碰撞和俯仰限制正常；角色不会穿过地面和墙壁。

## 13. Codex 协作约定

1. **先读本 GDD**：开始每项任务前读取 `docs/GDD.md`、`AGENTS.md`、`docs/TASKS.md`。
2. **一次一个里程碑**：先给出简短计划，说明将新增/修改的文件，再实施。
3. **禁止范围蔓延**：不得擅自新增联机、复杂技能树、商店、任务或其他非 MVP 系统。
4. **先可运行后精美**：缺少 Blender/MCP 时使用占位资源，不能假装生成了模型。
5. **代码可维护**：清晰命名、类型标注、分离职责、避免巨型脚本和循环依赖。
6. **每次验收**：运行可用的 Godot headless 检查，报告真实结果和人工测试步骤。
7. **不破坏既有工作**：检查 Git 状态，不覆盖用户未提交改动；修改尽量小且可回退。
8. **发现冲突**：GDD 与已有实现不一致时先报告冲突与建议，不自行重定义玩法。
9. **更新任务清单**：完成一个里程碑后更新 `docs/TASKS.md`，记录完成、遗留与下一步。
10. **人工决策**：涉及核心玩法改变、美术风格重大变化或新增依赖时先征求确认。
